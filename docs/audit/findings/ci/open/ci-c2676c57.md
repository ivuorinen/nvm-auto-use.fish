# Gate-shaped workflows are not required status checks

## Problem

Class: non-gating-check. Verified.

`Lint` and `PR Lint` both trigger on `pull_request` and run linters/validators, so
both are gate candidates. The repository's only ruleset (`main`, id 4676324,
enforcement `active`) contains no `required_status_checks` rule, and classic
branch protection is absent. Nothing blocks a merge on a red check.

## Evidence

`gh api repos/ivuorinen/nvm-auto-use.fish/rulesets/4676324` rule types:
`deletion`, `non_fast_forward`, `creation`, `required_linear_history`,
`pull_request`, `copilot_code_review`. No `required_status_checks`.

`gh api repos/ivuorinen/nvm-auto-use.fish/branches/main/protection`
-> 404 "Branch not protected".

Consequence already observed: `PR Lint` concluded `failure` on every open
renovate PR since 2026-08-03 (runs 30777396138, 30777392536) and those PRs
remained mergeable. A genuinely broken `editorconfig-checker` installer also
sat on `main` undetected, because no required check exercised it.

Check-run names confirmed against PR #10 head
(`gh api repos/ivuorinen/nvm-auto-use.fish/commits/<sha>/check-runs`):
`Lint codebase` (success), `Lint on pull request` (success),
`Lint on push` (skipped).

## Impact

Any PR can be merged into `main` with lint and workflow-security checks red.
The `pull_request` review rule requires 1 approval but approval does not read
check status, so a broken change merges on a rubber-stamp review.

## Fix

Add a `required_status_checks` rule to ruleset 4676324 with the two
pull-request check-run names as contexts. Never auto-applied — the user runs
it.

`PUT` replaces the **entire** ruleset and rejects the server-managed fields the
`GET` returns, so the field-stripping and the rule update must both actually
execute. Requires `jq` (installed by `make install-tools`). The commands below
avoid shell-specific control flow so they work in `fish`, `bash`, and `sh`
alike.

Step 1 — fetch, strip server-managed fields, set the rule:

    gh api repos/ivuorinen/nvm-auto-use.fish/rulesets/4676324 > /tmp/rs.json

    jq 'del(._links, .created_at, .updated_at, .id, .node_id,
            .source, .source_type, .current_user_can_bypass)
        | .rules = ((.rules | map(select(.type != "required_status_checks")))
          + [{
              "type": "required_status_checks",
              "parameters": {
                "strict_required_status_checks_policy": true,
                "do_not_enforce_on_create": false,
                "required_status_checks": [
                  {"context": "Lint codebase"},
                  {"context": "Lint on pull request"}
                ]
              }
            }])' /tmp/rs.json > /tmp/rs-updated.json

`.rules =` with the type filtered out replaces any existing
`required_status_checks` rule rather than appending, so re-running the
procedure is idempotent and cannot accumulate duplicate rules.

Step 2 — confirm nothing changed server-side since Step 1, then `PUT`:

    gh api repos/ivuorinen/nvm-auto-use.fish/rulesets/4676324 > /tmp/rs-recheck.json
    jq -S . /tmp/rs.json         > /tmp/rs-a.json
    jq -S . /tmp/rs-recheck.json > /tmp/rs-b.json
    diff /tmp/rs-a.json /tmp/rs-b.json

If `diff` prints anything, the ruleset was edited between Step 1 and now —
discard everything and start again from Step 1. Only when `diff` is silent:

    gh api -X PUT repos/ivuorinen/nvm-auto-use.fish/rulesets/4676324 \
      --input /tmp/rs-updated.json

This narrows the read-modify-write window; it does not close it. GitHub
documents no `If-Match`/conditional-update support for this endpoint, so a
concurrent edit landing between the `diff` and the `PUT` would still be
overwritten. Run it when no one else is editing repository rulesets.

Step 3 — verify the contexts landed, not merely that the rule type exists. A
`required_status_checks` rule with an empty array gates nothing:

    gh api repos/ivuorinen/nvm-auto-use.fish/rulesets/4676324 \
      --jq '.rules[] | select(.type=="required_status_checks")
            | .parameters.required_status_checks[].context'

Expected output, exactly these two lines:

    Lint codebase
    Lint on pull request

`Lint on push` is deliberately excluded, but not because it would block
merges. Its job-level `if: github.event_name == 'push'`
(`.github/workflows/pr-lint.yml:20`) skips it on `pull_request` events, and a
job skipped by a job-level condition reports `Success` — confirmed on PR #10's
head, where the `Lint on push` check-run carried conclusion `skipped`, not
pending. Requiring it would therefore add a permanently green check that
validates no pull-request linting at all.

The pending-check trap that does block merges applies to workflow-level
skips — `paths`, `paths-ignore`, `branches`, or `branches-ignore` filters that
stop the workflow from starting, so no check-run is ever created.
`pr-lint.yml` triggers on both `push` and `pull_request`, so its workflow
always runs on a PR and both jobs always report.
